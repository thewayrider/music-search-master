# Architecture Report: Web Scraping Degradation & The Linux Sandbox Solution

**Project:** `music-search-master` (Antigravity Fleet)  
**Date:** October 19, 2026  
**Environment:** Transitioning from Cloud IDE (Vercel/GitHub Actions) to Local Googlebook OS Linux Sandbox  

---

### 1. The Core Issue: Cloud Datacenter IP Shadow Banning

During the extensive cloud-based development of the `music-search-master` project (which features 15 different scraper forms, including `newReleasesNowAgent.js` and YouTube/SoundCloud crawlers), we observed significant performance degradation. Specifically, the scrapers were consistently returning poor results or empty arrays despite the code structure and CSS selectors being correct.

The root cause was diagnosed as **datacenter IP blocking (shadow banning)**. When a Node.js scraper runs from a massive cloud environment like Vercel or AWS, target servers (like YouTube or indie music blogs) instantly flag the request as automated bot traffic. Instead of crashing the script with a hard 403 error, these sites degrade the payload:

* **CAPTCHA Traps:** Sending consent walls instead of music metadata.
* **Stripped DOMs:** Refusing to load the dynamic JavaScript frameworks that populate the page, returning a skeleton HTML file.
* **Silent Throttling:** Artificially delaying requests until the crawler times out.

---

### 2. The Local Network Test (Proof of Concept)

To verify this diagnosis before the arrival of the Lenovo Googlebook, a local test was conducted on the existing Geekom Mini PC in Lugano.

**Methodology:**
1. The `music-search-master` repository was cloned locally to the Geekom PC via VS Code terminal.
2. The specific weekly scraper agent, `src/crawlers/newReleasesNowAgent.js`, was isolated.
3. Temporary Node.js `fs.writeFileSync` code was appended to the agent to output the raw JSON results directly to a local file (`test_results.json`), bypassing the unreadable terminal log dump generated by the Antigravity system logs.
4. The scraper was executed via the local Node environment (`node src/crawlers/newReleasesNowAgent.js`).

**Results:**  
The test was definitively successful. By routing the request through the Geekom PC connected to a standard Lugano residential Wi-Fi network, the target servers saw normal human traffic rather than a cloud server. The security algorithms dropped their defenses, serving the full HTML payload.

The `newReleasesNowAgent.js` successfully executed its loop, finding 103 distinct candidate releases across 5 genre channels (indie rock, pop, folk, alternative, and post-punk) without triggering a single block or CAPTCHA trap.

---

### 3. Architectural Directives for the Googlebook Re-Code

Based on this successful test, the upcoming re-code of the `music-search-master` project using the Lenovo Googlebook OS Linux sandbox must adhere to the following workflow changes:

* **Sandbox Isolation vs Network Access:** The new Linux sandbox will provide the security of file-system isolation (protecting the main Googlebook OS from destructive agent commands) while still utilizing the laptop's live residential IP address to bypass web scraper blocks.
* **Decoupled Development:** The Antigravity IDE and crawler authoring will move entirely inside the local Googlebook Linux container.
* **AI Offline Routing (Optional):** Because the sandbox is a Debian environment, the IDE can be configured via Tailscale to route AI reasoning requests to local offline models (like Llama/Qwen running on the Geekom), avoiding cloud API token costs entirely during heavy development phases.
* **Local Data Verification:** For debugging crawler outputs during the rebuild, developers should utilize the `fs` module to write clean `.json` output files locally, rather than parsing the `console.log` system dumps inside the terminal.
